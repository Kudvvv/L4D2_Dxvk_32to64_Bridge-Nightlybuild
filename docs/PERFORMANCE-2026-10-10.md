# 2026-10-10：L4N 固定回放性能验证

本轮优先检查 1% / 0.1% low，再看平均帧和峰值。保留偏色修复、GPLALL 后端、原画质、Mod 和默认配置，没有引入游戏功能。性能测试全程保留原始 `studiorender.dll`，没有应用 ThinFlex 引擎补丁。后续发布包会包含 ThinFlex 修复工具；本报告的性能数据对应未应用该工具的状态。

## 改动与自动化验证

1. 关闭 API 日志时，避免为每次函数调用临时构造 `std::string`；启用日志时仍拥有名称并保留原日志行为。
2. 只有完整表面、正数且紧密匹配的 pitch、校验一致的总长度才采用整块复制；部分区域、带 padding、ATI 和共享堆路径保留原处理。
3. 将普通定期内存扫描交给线程池，最多保留一个待完成任务；强制失败仍同步记录并刷新。DLL 临时引用覆盖排队和执行，不在 DllMain 新增等待。详见 [采样语义和生命周期](MEMORY-DIAGNOSTICS.md)。

两项复制／日志候选：`35bf2341c82b5bca92ebb5e9d05993d714088a08`，验证构建 [37965331629](https://github.com/NPCodex/L4D2_Dxvk_32to64_Bridge-Nightlybuild/actions/runs/37965331629)。最终三项候选：`7bc830169844de1e02fada926f374debc758d645`，验证构建 [37966476999](https://github.com/NPCodex/L4D2_Dxvk_32to64_Bridge-Nightlybuild/actions/runs/37966476999)。上述两次构建均为 `validation_only`，未执行发布步骤。

两次完整构建均通过 Python 回归、x86 Client / x64 Host 编译、资源与队列测试，以及真实上传代码的正常和负向对照。最终候选额外通过 x86/x64 真实 DLL 测试：排队／执行中卸载、事件文本所有权、五秒节流、忙时合并、调度失败回退，以及强制诊断并发时同步刷新且不调用 C++ new。

## 周期性慢帧证据

原版 60 秒诊断捕获中，12 次普通内存采样均位于对应的 Host 长帧区间，并全部进入最慢的 0.1% 帧集合。相关帧平均 10.42 ms，普通帧中位 3.23 ms，而相关帧 GPU 活动平均 3.24 ms。当时存在两个命令辅助进程的额外 CPU 负载，因此该段只用于定位周期性延迟，不作为干净的 FPS 基线；正式对照前已关闭辅助进程。这支持同步扫描路径造成额外延迟；没有 CPU 堆栈跟踪，不能把全部延迟单独归因于 VirtualQuery。

首组有效 90 秒对照中，原版和异步版均完整记录 18 次普通采样，全部 `scan_complete=1`、`counters_valid=1`，无失败事件。采样附近 ±20 ms 窗口内的最大帧间隔平均从 9.93 ms 降到 4.55 ms；存在 ≥8 ms 慢帧的窗口由 18/18 降至 0/18。候选包含三项改动，因此不能把所有平均帧变化归因于采样器。

### 配对结果

最终比较基线 v1.0.6 与三项性能候选 v1.0.11，共三对、六轮有效捕获。每轮均通过相同的完整性检查，固定配置和录像哈希一致，同一版本的 Client/Host 二进制哈希一致。下表 FPS 保留两位小数；完整精度、帧时间指标及每轮原始 CSV 哈希见 [游戏结果 CSV](benchmarks/2026-10-10/game-results.csv)，版本、校验结果、逐对变化和排除记录见 [测量来源与方法](benchmarks/2026-10-10/game-provenance.json)。

| 配对 | 轮次／版本 | 1% low | 0.1% low | 平均 FPS | 一秒 Present 峰值 |
|---|---|---:|---:|---:|---:|
| 1 | baseline03／基线 | 175.33 | 106.45 | 336.63 | 350 |
| 1 | async01／候选 | 183.34 | 136.45 | 373.03 | 380 |
| 2 | baseline05／基线 | 178.27 | 103.90 | 342.86 | 355 |

下面先计算每对的相对变化，再取三对的中位数及最小／最大值；不是两组中位 FPS 的比值。正值表示改善，负值表示退步；帧时间和慢帧数量以减少为改善方向。

| 指标 | 配对改善中位数 | 三对范围 |
|---|---:|---:|
| 1% low | +4.57% | +3.47%～+7.01% |
| 0.1% low | +33.09% | +28.18%～+38.13% |
| 平均 FPS | +10.14% | +9.56%～+10.81% |
| 一秒 Present 峰值 | +7.89% | +6.78%～+8.57% |
| p99 帧时间 | −3.48% | −4.74%～−1.08% |
| p99.9 帧时间 | +24.03% | +22.05%～+27.76% |
| ≥8 ms 帧数量 | +63.33% | +57.14%～+72.41% |

三对的 low、平均 FPS 和一秒峰值均提高，但 p99 延迟也均增加了 1.08%～4.74%，不能据此声称全部帧时间指标改善。最坏单帧也有波动：首对从 11.52 ms 增至 12.34 ms，另外两对从 17.25／10.97 ms 降至 9.36／10.28 ms。每轮 ≥8 ms 帧数分别从 30／29／28 降至 11／8／12；周期性慢帧减少后，仍有其他慢帧存在。

1% / 0.1% low 定义为 `1000 / 最慢 ceil(N×比例) 帧的平均毫秒数`。一秒峰值使用按经过时间划分、互不重叠的一秒区间中的 Present 数，并排除首尾区间；不是滑动窗口最大值。单帧倒数的瞬时最大 FPS 保留在数据中，不作为可持续峰值或输入延迟的证据。Present 间隔表示 Host 提交节奏，不等同于显示器实际显示完整画面的次数。

## 证据与边界

本地原始帧 CSV、两侧日志、配置及二进制哈希、采样时钟校准和排除原因保存在 `results/performance-20261010-resume/`。公开表仅保留汇总指标和证据哈希，游戏日志与录像保留在本地。

`copy-logger01` 因采样内失焦并出现 QPC 倒序、零间隔而整轮排除；`copy-logger02` 因采样内约 46.87 秒处于后台而整轮排除；`baseline04` 因恢复前台晚于采样起点、且随后还有焦点切换而整轮排除。没有选取其中较好的分段代替成绩。因此没有有效的两项候选游戏对照，最终结果只评价三项组合。

三对均按基线→候选的顺序运行，没有随机化顺序。预热从进程启动计时，没有严格对齐到同一录像 tick。帧之间存在相关性，不能把每一帧当成独立重复；这里报告三次配对观察及范围，没有给出统计置信度。此前 `baseline01`／`baseline02` 使用 30 秒预热，仅为先导捕获，不进入最终比较。

这是单台机器、一个固定回放场景的短时对照，不能代替激战场景、连续换图或长时间稳定性测试，也不能承诺其他玩家获得相同百分比。原版和候选均正常退出；每轮结束会恢复备份的原版 Client/Host，并检查后端、引擎 DLL 和图形配置哈希。
