# 首次带全部 Mod 进入战役的实测记录

用户报告：Intel Arc B580，DXVK 2.6.1 x64，保留全部原有 Mod，使用客户端更新包正常进入游戏，运行流畅且未观察到掉帧。客户端对应提交 787794861c208b66c3ae55484d2dde746b87756f，Windows 构建和 x86 自动测试通过。游戏构建号、Intel 驱动版本、具体地图名及定量 FPS 未提供。

## 日志证据

本次 bridge32.log 和 bridge64.log 的 GUID 一致。Host 明确运行在 x64 模式，加载 .l4d2bridge/d3d9vk_x64.dll 的普通 DXVK 后端，CreateDevice 返回 0x00000000，1920×1200 窗口模式。23:16:56–23:20:27，约 210 秒，客户端发送 Terminate，Host 正常清理退出。没有记录客户端意外退出、设备创建失败或桥接超时。

l4d2-memory.log 包含 42 次采样（23:16:57.903–23:20:23.552），全部 scan_complete=1、counters_valid=1，没有 allocation-failed、section-create-failed 或 section-map-failed。surface_view_budget_bytes 的最大值为 134,217,728 字节，正好 128 MiB。

23:17:42.912，保留的纹理数据约 2129.74 MiB，与上一轮进图崩溃前的 2128.59 MiB 接近。新客户端只映射 116.20 MiB，空闲地址空间 2199.63 MiB，最大连续空闲块 1335.38 MiB；上一轮分别约 147.14 MiB、55 MiB。这一相近纹理数据规模的采样支持回收机制显著减轻了 x86 地址空间压力。

23:18:18.528 起到最后采样，保留数据约 2569.94–2570.44 MiB，映射约 106.88–107.05 MiB，缓存预算不超过 128 MiB。x86 空闲地址空间约 2156.21–2163.74 MiB（约 2.11 GiB），最大连续空闲块保持 1335.38 MiB（约 1.30 GiB）。这段约两分钟的采样没有持续的大幅增长，但不能据此排除长期泄漏。

## 统计解释与验证范围

用户的 mem_dump 显示 Used=-32 MB、Free=4096 MB，该组 OS 读数异常，不能用于判断真实进程内存或地址空间。无法仅凭输出确定异常原因。Datacache 的 412.53 MB 是引擎列出的缓存分类总量，不代表游戏进程、桥接副本和 x64 Host 的全部内存。

用户另观察到 L4N 的 AV 约 2000 MB，比无桥时多 500 MB 以上。本次 VirtualQuery 采样支持约 2 GiB 剩余地址空间；无桥对照日志未提供，因此没有独立确认相对无桥的 500 MB 收益。

本次通过的是：x86 → x64 DXVK 呈现、全部既有 Mod 首次进图、纹理映射预算回收和正常退出。分页文件支持的 section 仍保留约 2.51 GiB 数据并消耗系统提交量，不能将地址空间收益解释为同等物理内存节省。游戏引擎仍为 x86，长期运行、连续换图、Reset 和精确性能差异未完成验证。

bridge32.log 的 Direct3DQuery9_LSS::Release “Missing function” 仍存在；源码实际调用 D3DBase::Release，不能把该日志等同于 Release 被忽略。本次正常退出也没有提供由它引起失败的证据。

下一轮保留相同二进制和配置：游玩至少 30 分钟并连续换图 3–5 次，观察贴图、帧率和内存，退出后保存两侧桥接日志及 l4d2-memory.log；崩溃时立即保存日志和可用 dump。之后在同一地图、位置、画质和 Mod 下与无桥基线比较帧率与地址空间。
