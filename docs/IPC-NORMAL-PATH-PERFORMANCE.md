## 实际调用链和成本来源

Client API → `Bridge::Command`（已有 mutex、UID、异常上下文）→ reservation / `syncDataQueue` → `CircularBuffer` 写字段、长度、padding、payload → `finish` → release 发布数据末端 → Header queue 发布和通知。

Host → `waitForCommand` / Header `peek` → `pop_front` / `startRead` → 校验协议和发布边界 → `get_data` / serializer 读取 → handler 实际使用数据 → `end_read_data` 校验完整包末端 → SC 发布消费和检查 waiting。Host 回复及 Client 匹配 UID 消费使用相同传输职责；Client 先完成 payload，后移除回复 Header，以 release/acquire 把消费状态交给下一 UID waiter。

优化前普通 UID + 两个字段 + Blob 包：Client 至少三次 reserve，同一 reservation 在 Bridge 与 CircularBuffer 重新计算；环尾字段拆写还逐字段更新逻辑游标。Host 逐字段检查并再次规划读游标。`pbCmdInProgress` 的两次默认 SC store 属于本地诊断标记；Header 已到达时 `peek` / `pull` 仍读取 GetTickCount64，`peek` 在 acquire 后还有 SC fence。每个成功提交也计算异常路径需要的 retry budget。x86 的 64-bit 逻辑游标与原子 published/consumed 本身另有必要成本。

## 本次改变及保留的不变量

1. 规划结果传给私有 reserved serializer，执行原先已经验证的同一个 plan，取消重复规划。公开 standalone queue API 仍进行完整检查。环尾字段写入一次推进游标。
2. 已知单 Blob / 标量布局使用 `Packet`：把 UID、字段、长度、padding 和 payload 统一规划、检查完整占用、预留一次；成功只发布一个 Header。Host 验证全部 metadata 后才读取不可信长度，再检查完整跨度恰好到达 Header 末端，一次推进剩余字段的读游标，handler 完成后确认消费一次。生产 Host 仍先用通用入口读取公共 UID，因此实际分派含 UID 与剩余布局两次本地游标推进；不把测试中 UID 一并读取的最理想形式当成生产收益。所有包大小使用同一规则。
3. 单调已 acquire 的 published 下界保存在通道中。只有新 Header 超过该下界时刷新；缓存不会扩大已验证空间，也不能绕过协议、Header offset、整环标记、overflow 和包末端检查。
4. 本地活动标记使用 relaxed；原 Client mutex / Host 单写者契约保持。标记不负责数据发布或占用授权。
5. Header 非满队列先 `try_push`，无需计算 retry budget 或创建满队列诊断；空队列才初始化等待时钟。`peek` / `pull` acquire 消费索引和生产索引，分别承接 UID 交接与 Header 发布；去掉多余的 SC fence。
6. `startRead` 已验证完整包跨度、容量和 overflow；每次标量读取只需确认 `cursor < readEnd`，即可证明 `cursor + 1 <= readEnd <= UINT64_MAX`，不必重做 reservation 规划。实际内存位置始终由队列构造和 `advanceTo` 保持在容量内。Blob 必须先验证长度字段可读，再读取不可信长度并完整规划；未减少 Blob 检查。
7. 普通 Command 与整包 Command 共用一个构造实现，以 `includeUid` 决定是否在该入口发送 UID。普通调用者仅有可内联的固定参数包装，避免先调用另一构造函数、返回后再单独发送 UID的额外调用。原 mutex、会话健康检查、异常展开和 finish 规则保持。
8. 前一轮整包 `packetAt` 内部仍执行字段与 Blob 两次 `planAt`。最终候选直接计算字段、长度、padding 和 payload 的完整 footprint，只对完整值做一次容量 / cursor overflow 判断；先限制 prefix、物理位置与 uint32 wire length，确保中间加法在 uint64 范围内。不是删除任何必要条件：原逐段规划保留为独立参考，542,385 个布局及额外 7,200 个 0 / 1 / UINT32_MAX 容量、极端 prefix、cursor 接近 UINT64_MAX 的用例验证接受集合与布局相同。

SC 的数据 waiting 登记、consumed 发布、相对重查及 Header armed-wait 协议全部保留。通知仍不授予空间。累计批次不得超过容量，padding 算占用，超大或 cursor overflow 拒绝。取消、fault、异常展开、未闭合 Blob、Header 满载失败继续 poison，失败后不能发布后续 Header。消费 ack 在实际使用结束后发生；optimized Lock 的 pin/unpin/Destroy 保护不变。

共享 control 仍为 64 字节，Header 仍为 12 字节；没有新增共享 ABI、mutex、哈希表、等待线程或 payload 分配。新增本地存储为每个通道一个 8-byte `cachedPublished`，每个活跃 Command 一个原生指针（x86 4 / x64 8 字节）；Packet / 规划结果是栈上短时对象。Device / Module 各一个 reader、一个 writer，四个通道的缓存字段合计增加 32 字节/进程。MSVC fixture 实测 Channel x86 88→96 / x64 152→160，Command x86 136→136（利用原有对齐空隙）/ x64 152→160；这两个候选只改变 planner 算术，不改变类型布局。原有特殊 pin 状态不增加。

整包入口首批用于 `SetStreamSource`、`SetIndices` 及 VB/IB Unlock。绑定仍全部转发，不过滤同值。VB/IB 的 FULL_SHADOW、Lock、上传范围/内容、SharedHeap 与 optimized Lock 的资源所有权、DXVK 后端不变；仅合并已有 Unlock 的 serialization。Host 在 backend Lock 前先校验完整上传长度，失败不执行 backend copy。其他增量/多 Blob 命令继续使用受检查的通用接口，受益于 reservation 复用和 Header 快路径，尚未全部迁移。

## 可重复测量方法

A：v1.2.1 原生产源码、原 Device 消费完成块；B：冻结的优化前 PR #6；C：本次生产实现并使用整包入口。保留最初同一编译单元的 A/B/C 对照，并补充另一组分开编译调用者与 Command 实现的 A/B/Q/C。补充组也保留生产 Host 先读取 UID、再解包剩余字段的顺序；8 个正常场景、同样预热与 11 轮轮换及反向顺序，不替换原结果。三者使用同一机器、同一 MSVC 14.29 `/O2`、同一 disabled diagnostics / OS adapter、相同 UID/两个字段/Blob wire 布局。分别覆盖 x86/x86 和 x86/x64。每场景预热一次、11 轮，以 ABC 六种顺序轮转。批次外层 QPC、GetThreadTimes、QueryThreadCycleTime 记录提交、消费和 Client 端到端完成；不在单调用内加计时或计数。

原 counts/capacity/deadline 和 payload 校验保持：0/64/1024/4096/65536 B 无竞争批次，连续 64 B，4096 DWORD 环的 99.6% 占用、回绕、每 64 包 Sleep(1) 慢消费者，500 ms idle。大批次容量为 8,388,608 DWORD（32 MiB），并非生产扩容。旧 A 超时保留失败记录，不参与有效性能比例；B/C 或归因变体任何原生失败立即停止实验。

分阶段归因也在相同 job、两种 Host 位数下进行，0/64 B batch 与 64 B stream 各预热一次及 7 轮轮转：

| 变体 | 实际来源及用途 |
|---|---|
| B | 冻结 PR #6 原实现 |
| F | B 仅把本地活动 flag 改 relaxed |
| R | 本次通用 reservation / 标量读取 / 下界缓存、构造入口与活动 flag，但 Header queue 和 finish budget 仍使用 B |
| Q | 本次全部通用热路径，以编译期固定 generic 布局的独立 exe 执行 |

F/R 从生产源隔离复制并明确变换，不在计时路径加入诊断。所有源哈希和 assembly 随证据构件保存。阶段之差代表该组改动在该负载中的净效应，不是逐条 CPU 指令成本；R 含多项协同变化，不能声称单独量出每个边界分支的 ns。最终 Q/C 各自编译固定布局，B/F/R/Q 的 generic 循环结构一致；布局参数只在批次外验证，计时循环没有运行时布局选择。

早期两个成功 run 使用同一个 C exe 在循环内选择 generic / known，改变了 MSVC 内联和寄存器分配，R→Q 因此并非纯 Header 成本。保留这些原始证据，最终归因采用修正后的独立编译，不据此预设 Header 优化有效或无效。另保留原始 A/B/C 同编译单元实验与更接近生产调用边界的 separate-caller 实验，最终建议以两者相互核验，不能只选更快的一组。

### 净收益、残余开销与决策

1. **可以优化 PR #6 的额外成本。** 在实际调用边界的 x86→x64 64 B 对照中，C 对 B 配对减少 Client 63.12 ns / Host 65.75 ns，cycles 分别减少约 27.46% / 53.59%；实际端到端配对减少 131.30 ns/包（−36.84%）。x86 Host 下 Client −26.56%，端到端 −28.61%。这些负载没有减少命令数或上传字节，减少的是实际执行成本；不能把两侧百分比相加。
2. **通用路径收益与整包收益必须区分。** 独立调用者的 x64 Host 通用 Q 从 B 的 124.70 降到 52.18 ns，配对 −58.04%；Client Q 为 217.31 ns，对 B 配对 −6.88%，范围 −22.62%～+9.36%，不能保证每轮都加速。Q→C Client 配对再减少 51.86 ns，Host 增加 6.36 ns，最终端到端仍减少 43.45 ns（−15.86%）。整包的前置完整形状验证、字段结果对象及分派顺序有成本，不预设两端单独都更快，也不按包大小选择更弱的读取规则。
3. **主要 Host 恢复来自复用已有证明，活动 flag / Header 微调不能单独解释约 100 ns。** F→R 的 scalar bounds、reservation 复用、单调进度缓存与构造形态是一组变化，64 B 归因中 Host32 / Host64 净减少约 74 / 82 ns。Header R→Q 的 Client 变化仅约 −1.6 / −2.7 ns、范围跨零；x64 Host 也不稳定。不能把成组结果解释成每个检查或每条原子指令的精确价格。移除诊断 flag 的 SC store 在源码和汇编中有依据，但单独阶段没有稳定 Host wall 收益。
4. **恢复原版的目标未达到。** 同轮 x86→x64 64 B 的 A→C 残余中位数为 Client +45.47 ns、Host +22.08 ns，cycles 同样增加，端到端 +68.49 ns（+43.76%）。0 B 的 Client 仍约 +50%，连续 64 B / 回绕分别约 +9.7% / +13.1%；两组编译实验都保留明显小包退化。64 KiB Client 变化小且范围跨零，不能宣称稳定收益；x86 大包还有宽幅波动，所有合法样本已保留。
5. **尚未解决的成本已明确，但没有证明这些成本都不可消除。** Client 仍承担会话/fault 检查、异常展开识别（构造及 finish 的 `std::uncaught_exceptions`）、64-bit 逻辑游标、原子 published 发布和可靠 Header 提交；Host 保留完整 Header/跨度验证、前置布局验证，以及 SC consumed/waiting 协议。原版没有这些完整的失败停止和跨进程原子保证。现有归因没有单独计量 CRT 异常状态查询或每次 64-bit 原子的价格，不能将剩余 45 ns 全部武断归于某一个项目；也不能删除这些保证追平 A。部分多 Blob / 增量 API 尚未采用整包入口。
6. **本次停止扩大优化范围，保持 Draft。** 保留已验证且能降低 B 成本的候选供审查，但不建议按“已恢复原版性能”合并或发布。不扩大 FULL_SHADOW、锁、上传、后端、协议或资源追踪改动；不批量迁移更多 API 来制造命令/规划次数漂亮的统计。若继续研究，优先在同机隔离上述残余成本，再以相同回归和正常路径门槛验证；不得降低校验、失败传播或等待保证。当前结论是“有净收益，但此候选性能验收不通过”，不是对所有未来 IPC 优化宣称不可能。

### 成本模型与适用范围

Client 成本可以写为 `已有 Command/锁成本 + 批次及失败状态检查 + 布局规划与本地游标维护 + payload 复制 + 发布/通知`；Host 为 `Header 获取 + 包边界/布局验证与本地读游标 + handler 使用 + consumed/waiting 发布`。整包入口减少规划次数、本地写游标推进和同步空间确认，不省略 Header、不减少 payload 字节、不合并独立 D3D9 命令。实验中的 A/B/Q/C 每组成功样本都提交相同数量的命令与相同 wire 字节，收益来自每包 CPU 成本变化。

通道已 acquire 的进度缓存是保守下界：容量判断失败才读取新进度，不增加空间授权。正常路径仍检查会话取消 / fault、批次容量和整数 overflow；finish 仍再次检查会话、Blob 完成及异常展开，防止写入期间故障后继续提交。这些检查出现在不同阶段，有各自的失败边界，不能单凭名字相似删去。SC consumed/waiting 登记重查是丢失唤醒修复的一部分；x86 的共享 64-bit published/consumed 读写也必须保持原子性，不能退回 v1.2.1 的普通共享读写。分阶段实验能够量出成组净收益，不能给每一条必要验证或原子指令单独分配精确 ns。

这组固定布局传输使用生产 queue、Bridge、serializer、shared memory 和 semaphore 源码；日志、选项、peer/dispatch 周边由共同适配器提供，诊断关闭，handler 仅验证数据。完整构建使用仓库既定设置，计时 fixture 使用一致 `/O2`。separate-caller 保留无 LTO 的实际 Command 调用边界和公共 UID 分派顺序，但没有运行全部 Host D3D9 switch、backend Lock/copy、DXVK 或 GPU。大包 Host 仅使用并检查开头/结尾，不代表 GPU 上传复制速度。绝对数值和游戏收益须由实机验证，当前证据足以判断这个候选在正常传输测试中是否达到相对原版的门槛。
