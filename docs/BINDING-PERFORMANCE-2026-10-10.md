# 重复缓冲区绑定的引用开销

本轮以 v1.1.10（`bcacb4727007ad040f0f6447a4e258f0456469de`）为基准，目标是减少 Bridge 在手电场景中的额外 CPU 工作。游戏帧率收益尚待验证；操作次数减少不等同于 FPS 或 low 帧提升。

## 改动范围

Client 的 `SetStreamSource` 与 `SetIndices` 在实际目标槽位已经持有相同资源时，省去临时智能指针引起的增减引用。四处判断分别覆盖当前设备状态和 StateBlock 捕获状态。判断位于原设备锁内；首次捕获仍独立持有资源，不同资源仍先持有新对象再释放旧对象。

所有 Host 命令、顺序、UID、参数、offset/stride 更新、dirty flags、诊断计数、可选响应等待和 HRESULT 保留。特别是 DrawUP 后，即使 Client 保存的资源指针相同，也仍发送重新绑定命令。没有降低画质、改变默认配置、添加功能或修改 CPU 调度策略。

## 回归与证据边界

测试从应用生产补丁后的源码提取完整 setter、`D3DAutoPtr`、StateBlock `StateTransfer` / `Capture` / `Apply` 和响应宏；原版由精确移除四处判断获得。COM 资源、锁、消息传输与诊断使用功能适配器。比较完整消息及状态轨迹，覆盖资源替换、null、参数变化、独立捕获、外部引用归零、销毁、Host 错误和超时。

本地 MinGW x86/x64 的同步模板及诊断开关组合通过，四个故意破坏行为的变体均被检出。每组 2,067 条消息及语义轨迹一致；2,000 次相同资源绑定的智能指针 retain/release 从 2,000/2,000 次降到 0/0 次。测试不是多线程互斥、实际跨进程 IPC 或完整 COM/Host 销毁协议验证；DrawUP 仅模拟 Host 绑定清空的效果。正式 MSVC 构建与原有原生回归由 Actions 执行。

生产补丁只替换 `d3d9_device.cpp` 的原补丁段，分别通过 NVIDIA 基准 `9aa74f8dfad2188efbd0f717c64d9f8fa909787e` 和固定构建源 `5fd30eae2d397f369bdf5660f3ddd0bc0bd1fa58` 的应用检查。未从含旧实验的依赖工作目录重新导出整份补丁。

## 未采用的队列实验

Host 缓存已 acquire 观察的队列发布边界，通过了 18 项正确性检查（含预期失败的负对照）。40 个微基准样本中，Host 方向容量 8 的吞吐配对中位改善约 12.96%，容量 256 仅约 0.22%；实际 Device 队列默认容量为 3072。证据不足以外推游戏收益，本轮没有将此候选并入生产。

## 游戏对照

沿用[上轮测试口径](FLASHLIGHT-PERFORMANCE-2026-10-10.md)，保持同场景、配置和匹配 GPLALL 后端，以 Present 间隔比较平均 FPS、1% low 和 0.1% low。双 CCD 的临时统一核心范围仅用于控制测试变量，不随包启用。上轮约 285 → 351 FPS 的调度差异不能计为本次代码收益。

最初基线因用户暂停以关闭垂直同步而中断，已排除；后一次会话在电脑控制中止后没有产生采样。原始记录和安装备份留在本地，不上传玩家日志。
